🎯 Contexte et règles du jeu

L'équipe produit d'Atelier Photo veut héberger son application sur Kubernetes. Vous êtes l'ingénieur DevOps de l'équipe : vous devez livrer une infrastructure entièrement décrite en Terraform, reproductible, sécurisée et documentée.

L'application est un service web qui écoute sur le port 8080. Elle stocke les photos dans Amazon S3 et leurs métadonnées dans PostgreSQL. Elle récupère les identifiants de la base dans Secrets Manager.

À la fin du week-end, vous saurez

  • Concevoir et découper un projet Terraform en modules réutilisables.
  • Créer un cluster EKS Auto Mode dans des sous-réseaux privés.
  • Donner des droits AWS aux pods sans aucune clé d'accès, grâce à Pod Identity.
  • Ouvrir une base RDS au security group du cluster plutôt qu'à une plage d'IP.
  • Générer des manifestes Kubernetes à partir des outputs Terraform.

✅ Autorisé

  • La documentation du Terraform Registry et d'AWS.
  • Les modules publics du Registry comme source d'inspiration (mais vous écrivez vos propres modules).
  • Les commandes docker, aws et kubectl pour construire l'image, vérifier et déployer.
  • La console AWS en lecture, pour observer.

⛔ Interdit

  • Créer ou modifier une ressource à la main dans la console.
  • Mettre une clé d'accès AWS ou un mot de passe dans le code, un manifeste ou Git.
  • Écrire en dur dans un manifeste une valeur que Terraform connaît (ARN, URL, nom…).
  • Ouvrir la base de données à 0.0.0.0/0.

💶 Budget : l'ensemble coûte environ 0,35 $ par heure (cluster EKS, NAT Gateway, RDS Multi-AZ, nœuds). Faites un terraform destroy à la fin de chaque session de travail. Votre code doit permettre de tout recréer en une commande.

🗺️ Architecture cible

C'est une architecture 3 tiers (publique, application, base) sur deux zones de disponibilité. La couche application est un cluster EKS Auto Mode. Auto Mode crée lui-même les nœuds EC2 dans les sous-réseaux privés quand des pods doivent être placés. Il crée aussi un ALB dans les sous-réseaux publics à partir de l'Ingress. Les pods obtiennent leurs droits S3 et Secrets Manager grâce à Pod Identity.

Le trajet d'une requête

  1. L'utilisateur appelle l'URL de l'ALB, placé dans les sous-réseaux publics.
  2. L'ALB transmet la requête aux pods sur le port 8080, dans les sous-réseaux privés.
  3. Le pod lit le mot de passe de la base dans Secrets Manager et écrit les photos dans S3. Ses droits viennent de Pod Identity.
  4. Le pod se connecte à RDS PostgreSQL sur le port 5432, dans les sous-réseaux « base ».
  5. Les nœuds téléchargent l'image depuis ECR et sortent vers Internet par la NAT Gateway.

Phase 1

Le réseau

⏱️ 1 h

Objectif : un VPC sur 2 zones de disponibilité, avec trois couches (publique, app, base), prêt à accueillir EKS.

Exigences

💡 Indices
  • Ressources à chercher dans le Registry : aws_vpc, aws_subnet, aws_internet_gateway, aws_eip, aws_nat_gateway, aws_route_table, aws_route_table_association.
  • La fonction cidrsubnet() permet de calculer les plages au lieu de les écrire : testez-la dans terraform console.
  • Les balises Kubernetes sont kubernetes.io/role/elb et kubernetes.io/role/internal-elb, avec la valeur 1. Cherchez dans la documentation AWS « EKS subnet tags load balancer » pour savoir laquelle va où.
  • Pourquoi les sous-réseaux « app » sont-ils si grands (/20) ? Pensez au nombre d'adresses IP consommées par les pods.
✅ Point de contrôle 
terraform apply
aws ec2 describe-subnets --filters "Name=vpc-id,Values=$(terraform output -raw vpc_id)" \
  --query 'Subnets[].[Tags[?Key==`Name`]|[0].Value,CidrBlock,AvailabilityZone]' --output table

Vous devez voir 6 sous-réseaux, répartis sur eu-west-3a et eu-west-3b, avec les bonnes plages.

Phase 2

Le registre d'images et l'image

⏱️ 45 min

Objectif : un dépôt ECR créé par Terraform, et l'image de l'application poussée dedans.

Exigences

💡 Indices
  • Ressource : aws_ecr_repository. Regardez ses options de scan et de suppression forcée.
  • La construction et l'envoi de l'image se font hors Terraform, avec docker et aws ecr get-login-password. Utilisez l'output de l'URL du dépôt plutôt que de la recopier.
  • Sur un Mac Apple Silicon, une image construite sans préciser la plateforme est en arm64 : elle ne démarrera pas sur des nœuds x86. Cherchez l'option --platform de docker build.
✅ Point de contrôle 
aws ecr describe-images --repository-name atelier-photo \
  --query 'imageDetails[].[imageTags[0],imagePushedAt]' --output table

Le tag eks-v1 apparaît.

Phase 3

Les données : S3 et RDS

⏱️ 1 h 30

Objectif : un bucket privé pour les photos, et une base PostgreSQL Multi-AZ dont le mot de passe n'apparaît nulle part dans votre code.

Bucket S3

Base RDS PostgreSQL

💡 Indices
  • Ressources : aws_s3_bucket et ses ressources de configuration séparées, aws_db_subnet_group, aws_security_group, aws_db_instance.
  • Dans aws_db_instance, cherchez l'argument qui demande à RDS de gérer lui-même le mot de passe principal. L'ARN du secret créé est alors disponible dans un attribut exporté de la ressource.
  • Le secret généré par RDS contient l'utilisateur et le mot de passe, mais pas l'adresse de la base : l'application devra la recevoir autrement.
  • La création d'une base Multi-AZ prend 15 à 20 minutes. Lancez-la, puis avancez sur la phase 4 en parallèle.
✅ Point de contrôle 
aws rds describe-db-instances \
  --query 'DBInstances[].[DBInstanceIdentifier,MultiAZ,PubliclyAccessible,AvailabilityZone,SecondaryAvailabilityZone]' \
  --output table
aws secretsmanager list-secrets --query 'SecretList[].Name'

MultiAZ = True, PubliclyAccessible = False, deux zones différentes, et un secret dont le nom commence par rds!.

Phase 4

Le cluster EKS Auto Mode

⏱️ 1 h 30

Objectif : un cluster EKS en mode Auto, dans les sous-réseaux « app », administrable avec kubectl. La base doit n'accepter que le trafic venant du cluster.

Exigences

💡 Indices
  • Dans aws_eks_cluster, Auto Mode repose sur trois blocs qui doivent être activés ensemble : compute_config, storage_config (stockage en blocs) et kubernetes_network_config (load balancing).
  • Avec Auto Mode, les add-ons auto-gérés par défaut ne doivent pas être installés : cherchez l'argument bootstrap_self_managed_addons.
  • Rôle du cluster : cherchez dans la documentation AWS « EKS Auto Mode cluster IAM role ». Il faut 5 policies managées, et la relation de confiance doit autoriser deux actions STS, pas une seule.
  • Rôle des nœuds : cherchez « EKS Auto Mode node IAM role ». 2 policies suffisent.
  • Le security group du cluster est un attribut exporté de aws_eks_cluster (dans vpc_config). Pour la règle de sg-db, regardez aws_vpc_security_group_ingress_rule et son argument de référence à un autre security group.
  • Votre IP publique : curl -s ifconfig.me. Vous pouvez aussi la récupérer dans Terraform avec un data source http.
✅ Point de contrôle 
$(terraform output -raw configure_kubectl)
aws eks describe-cluster --name eks-atelier-<prenom> \
  --query 'cluster.[status,version,computeConfig.enabled,computeConfig.nodePools]'
kubectl get nodepools
kubectl get nodes

Statut ACTIVE, computeConfig.enabled = true, et les deux node pools general-purpose et system.

kubectl get nodes peut ne rien afficher : c'est normal. Auto Mode ne crée un nœud que lorsqu'un pod en a besoin.

Phase 5

Les droits des pods avec Pod Identity

⏱️ 45 min

Objectif : les pods de l'application, et seulement eux, peuvent lire le secret de la base et lire/écrire dans le bucket photos. Aucune clé d'accès n'est utilisée.

Exigences

💡 Indices
  • Ressources : aws_iam_role, aws_iam_role_policy (ou aws_iam_policy + attachement), aws_eks_pod_identity_association.
  • Le principal de confiance est le service pods.eks.amazonaws.com, avec les deux mêmes actions STS que le rôle du cluster.
  • Le data source aws_iam_policy_document est plus lisible et plus sûr que du JSON écrit à la main.
  • Pour S3, l'action de listage porte sur l'ARN du bucket, tandis que les actions sur les objets portent sur ARN-du-bucket/*.
  • Avec Auto Mode, l'agent Pod Identity est déjà intégré aux nœuds : aucun add-on à installer.
✅ Point de contrôle 
aws eks list-pod-identity-associations --cluster-name eks-atelier-<prenom> \
  --query 'associations[].[namespace,serviceAccount,associationArn]' --output table

Une association atelier / sa-atelier.

💡 Indices
  • La fonction templatefile(chemin, { variables }) lit un modèle et remplace les ${…} par vos valeurs. Testez-la dans terraform console.

✅ Point de contrôle

kubectl apply --dry-run=client -f ../../k8s/atelier.yaml
grep -n "amazonaws.com" ../../k8s/atelier.yaml

🧹 Nettoyage — à faire à la fin de chaque session

L'ordre est important. L'ALB a été créé par Kubernetes à partir de l'Ingress : Terraform ne le connaît pas. S'il existe encore, il bloque la suppression des sous-réseaux et du VPC.

  1. Supprimer les objets Kubernetes : kubectl delete -f k8s/atelier.yaml.
  2. Attendre que l'ALB ait disparu : aws elbv2 describe-load-balancers --query 'LoadBalancers[].LoadBalancerName' ne doit plus le lister.
  3. Détruire l'infrastructure : terraform destroy, depuis envs/dev.
  4. Vérifier : terraform state list ne renvoie rien.

⚠️ Si vous détruisez le cluster avant l'Ingress, l'ALB et son security group restent orphelins. Il faudra alors les supprimer à la main dans la console EC2 avant de relancer terraform destroy, et le signaler dans votre README.
